## 1. Scope and Model

This specification defines a **snapshot-based Slowly Changing Dimension Type 2 (SCD2)** table.

Each execution processes a **complete snapshot** of the current source state. Deletes are inferred when a previously current natural key is missing from the incoming snapshot.

The model is **append-heavy with in-place closure** of current rows.

Out of scope:

* Late-arriving corrections that rewrite history
* Parallel or concurrent writes
* Deterministic ordering across rebuilds
* Reproducible surrogate keys or join numeric keys
* Real-time ingestion (batch only)

---

## 2. Table Schema

### 2.1 System-managed columns (mandatory)

| Column           | Type                  | Description                                                                                   |
| ---------------- | --------------------- | --------------------------------------------------------------------------------------------- |
| surrogate_key    | uint64                | Primary key. Unique, non-null, strictly monotonically increasing, never reused                |
| join_numeric_key | uint64                | Row-level numeric join key. Unique, non-null, strictly monotonically increasing, never reused |
| Row_Hash         | string                | Hash of tracked data columns                                                                  |
| Insert_Date      | datetime(3)           | Timestamp when the row was inserted                                                           |
| Update_Date      | datetime(3), nullable | Closure timestamp (end of currentness). Null for current rows                                 |
| Current_Ind      | bool                  | 1 = current row, 0 = non-current                                                              |
| Deleted_Ind      | bool                  | 1 = soft-deleted row, 0 = not deleted                                                         |

### 2.2 Natural key columns (mandatory)

One or more columns defining the business/natural key.
All natural key columns must be non-null.

### 2.3 Data columns (configurable)

Tracked attributes whose changes trigger SCD2 behavior.
User-defined constraints (non-null, uniqueness, defaults) are allowed.

---

## 3. Global Invariants and Constraints

The table must always satisfy the following:

1. `surrogate_key` is the primary key and is unique and non-null.
2. Natural key columns are non-null.
3. At most **one row per natural key** may have `Current_Ind = 1`.
4. `Current_Ind = 1` and `Deleted_Ind = 1` must never occur simultaneously.
5. A row may be **mutated only while it is current**, and only to close it.
6. After `Current_Ind` becomes 0, the row is immutable.
7. Row count behavior:

   * Inserts, updates, and reinsertions increase row count
   * Soft deletes do not increase row count
8. Incoming snapshots must contain **at most one row per natural key**.
   Duplicates are a hard error and must abort processing.
9. `Update_Date` is null for current rows and non-null for closed rows.
10. `join_numeric_key` is unique and non-null, must be **strictly monotonically increasing**, and must never be reused.
11. All changes from one execution are atomic.

### Monotonicity definition (for `surrogate_key` and `join_numeric_key`)

* “Created after” means **row creation order across successfully committed executions**.
* If row r2 is created after r1 (in commit order), then:
  `surrogate_key(r2) > surrogate_key(r1)` and
  `join_numeric_key(r2) > join_numeric_key(r1)`.
* Within a single successful execution that inserts multiple rows, assigned values must be **strictly increasing across the inserted rows**.
  Any internal ordering is acceptable.

---

## 4. Snapshot Semantics

Each execution receives a **full snapshot** of the source’s current state.

Let:

* `T` = existing SCD2 table
* `S` = incoming snapshot
* `K` = natural key

All comparisons are performed against rows in `T` where `Current_Ind = 1`.

---

## 5. Core Row State Transitions

### 5.1 Insert (new natural key)

Condition:

* `K` exists in `S`
* `K` does not exist in `T` with `Current_Ind = 1`

Action:

* Insert new row
* Assign new `surrogate_key`
* Assign new `join_numeric_key`
* Compute `Row_Hash` from tracked data columns
* Set:

  * `Insert_Date = execution_time`
  * `Update_Date = NULL`
  * `Current_Ind = 1`
  * `Deleted_Ind = 0`

---

### 5.2 No-op (unchanged)

Condition:

* `K` exists in both `S` and `T`
* Computed `Row_Hash` equals the current row’s `Row_Hash`

Action:

* No columns are written or updated
* No timestamps or flags are modified

---

### 5.3 Update (tracked attribute change)

Condition:

* `K` exists in both `S` and `T`
* Computed `Row_Hash` differs from the current row’s `Row_Hash`

Action:

1. Close existing current row:

   * Set `Current_Ind = 0`
   * Set `Update_Date = execution_time`
   * Leave `Deleted_Ind = 0`
2. Insert new row:

   * New `surrogate_key`
   * New `join_numeric_key`
   * New `Row_Hash`
   * `Insert_Date = execution_time`
   * `Update_Date = NULL`
   * `Current_Ind = 1`
   * `Deleted_Ind = 0`

---

### 5.4 Soft Delete (missing from snapshot)

Condition:

* `K` exists in `T` with `Current_Ind = 1`
* `K` does not exist in `S`

Action:

* Update the existing current row:

  * Set `Current_Ind = 0`
  * Set `Deleted_Ind = 1`
  * Set `Update_Date = execution_time`
* No new row is inserted

---

### 5.5 Reinsertion (after deletion)

Condition:

* `K` exists in `S`
* The most recently created row for `K` in `T` has `Deleted_Ind = 1`

Definition of “most recently created row for K”:

* The row for `K` with the greatest `surrogate_key`.

Action:

* Treat as a new insert:

  * New `surrogate_key`
  * New `join_numeric_key`
  * New `Row_Hash`
  * `Insert_Date = execution_time`
  * `Update_Date = NULL`
  * `Current_Ind = 1`
  * `Deleted_Ind = 0`

Previous rows remain unchanged.

---

## 6. Row_Hash Semantics

* `Row_Hash` is computed from tracked data columns only.
* System-managed columns are excluded.
* Hash algorithm and serialization are implementation-defined.
* Within a given deployment, the following must be deterministic:

  * Included columns
  * Column ordering
  * Null handling
  * Type normalization / serialization rules
* Cross-system hash equivalence is not required.

---

## 7. Surrogate Key Semantics

* `surrogate_key` uniquely identifies rows.
* Must be non-null, unique, strictly monotonically increasing, and never reused.
* Soft deletes do not generate new `surrogate_key` values.
* Updates and reinsertions generate new `surrogate_key` values.
* Not required to be reproducible across rebuilds.

---

## 8. join_numeric_key Semantics

* Assigned at row creation (inserts, updates’ new rows, reinsertions).
* Must be unique and non-null.
* Must be strictly monotonically increasing over time and never reused.
* Soft deletes do not generate a new `join_numeric_key`.
* Not required to be reproducible across rebuilds or across environments.
* Carries no business meaning.

---

## 9. Execution Context and Atomicity

1. All SCD2 logic must execute in a **single execution environment**.
2. All writes must occur within a **single transactional boundary**.
3. Intermediate staging tables or views are allowed only if atomicity is preserved.
4. On any error (constraint violation, execution failure, unexpected termination):

   * Processing must abort immediately
   * All changes must be rolled back
5. Partial application of a snapshot is not allowed.

---

## 10. Execution Time Semantics

* Each execution must capture a **single `execution_time` value**.
* This value must be used consistently for:

  * `Insert_Date`
  * `Update_Date`
* `execution_time` must be written at `datetime(3)` precision using deterministic rounding or truncation.

---

## 11. Idempotency

Given:

* The same initial table state
* The same snapshot input

Re-executing the process must produce **no net change** to the table.

No-op paths must not rewrite rows, timestamps, or flags.

---

## 12. Non-goals (explicit)

The implementation does not support:

* Rewriting or correcting historical rows
* Parallel or concurrent writes
* Deterministic ordering across rebuilds
* Reproducible surrogate keys or join numeric keys
* Real-time ingestion (batch-only assumption)
